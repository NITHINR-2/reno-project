# Decisions

One line per assumption or design choice, with its reason. Newest at the bottom of each phase.

## Phase 0 — Scaffold

- **Spring Boot 4.1.1 instead of 3.x** — Initializr only offers 4.x and 3.5 OSS support has ended; chosen by the project owner on 2026-10-10. CLAUDE.md stack line updated.
- **JUnit 6 (Jupiter 6.0.3) instead of JUnit 5** — it is what Boot 4.1 manages; the Jupiter API used in tests is unchanged.
- **springdoc-openapi 3.1.1** — the 3.x line is the one built for Spring Boot 4 / Framework 7.
- **Maven Wrapper 3.10.0 (script-only distribution)** — generated by Initializr; no wrapper JAR is committed.
- **JVM runs in UTC** (`TimeZone.setDefault` in `main`, `-Duser.timezone=UTC` for Surefire and `spring-boot:run`, `hibernate.jdbc.time_zone=UTC`) — Windows reports the legacy zone id `Asia/Calcutta`, which postgres:16 rejects at connect time; UTC storage is also correct practice, and IST (`Asia/Kolkata`) will be applied explicitly for SLA logic.
- **Single `application.yml` with `dev` and `test` profile documents** — keeps all config in one place, as the Phase 0 prompt asks.
- **Backend reads local secrets via `spring.config.import: optional:file:.env[.properties]`** — no extra dependency; `backend/.env` is git-ignored and `.env.example` documents the keys.
- **No default DB password anywhere in committed config** — compose fails fast if `POSTGRES_PASSWORD` is unset; the backend gets `DB_PASSWORD` from `backend/.env`. Follows "never commit secrets".
- **Test profile uses Testcontainers `@ServiceConnection` (postgres:16)** — tests are independent of the local compose database and match production's major version.
- **Flyway `V1__baseline.sql` is a no-op** — it exercises the Flyway wiring and history table before business tables exist.
- **`GET /api/health` is a custom endpoint (not Actuator)** — the prompt asks for this exact path; it reports `status`, `database` (via `SELECT 1`), `version` and `timestamp`, and returns 503 when the database is down.
- **Health endpoint and OpenAPI docs are `permitAll`; everything else requires authentication and returns 401** — secure-by-default baseline until JWT auth lands.
- **CSRF disabled and session policy STATELESS** — the API will be bearer-token based; the refresh-cookie CSRF guard (`X-Requested-With`) is added with the auth phase, per CLAUDE.md.
- **`GlobalExceptionHandler extends ResponseEntityExceptionHandler`** — gives ProblemDetail for all of Spring MVC's built-in exceptions plus a catch-all 500 that hides internals.
- **Health tests are `*Test`, not `*IT`** — the Boot parent doesn't bind Failsafe, so `*IT` classes would silently not run under `./mvnw verify`.
- **Vite 8 template's oxlint kept as the linter** — it is what `create-vite` 9 generates and `npm run lint` already uses it; no need to add ESLint.
- **TypeScript `strict: true` added explicitly** — the current Vite template no longer sets it, and CLAUDE.md requires strict mode.
- **Tailwind CSS v4 via `@tailwindcss/vite`** — the current official integration; no `tailwind.config.js` or PostCSS config needed. Brand tokens (`accent`, `charcoal`) are defined in `@theme`.
- **React Router 8 in data-router mode (`createBrowserRouter`)** — current stable; library mode keeps the SPA simple and leaves room for loaders later.
- **`@/` path alias → `src/`** — defined in both tsconfig and Vite.
- **Vitest without globals; explicit imports plus a `cleanup` in `src/test/setup.ts`** — avoids leaking global types into app code.
- **Health response validated with Zod on the client** — catches contract drift early; the backend stays the source of truth.
- **The Vite proxy target is configurable through `VITE_API_PROXY_TARGET`** (default `http://localhost:8080`).

## Phase 1 — Schema, JPA, auth

- **Entity list derived from CLAUDE.md (approved by the project owner, 2026-10-10)** — the original spec's list isn't in the repo. 20 tables: roles, permissions, role_permissions, users, regions, dealers, plants, vehicle_models, vehicle_variants, inventory_locations, inventory_stock, fleet_requests, stock_allocations, quotations, quotation_line_items, payment_receipts, production_orders, dispatches, workflow_history, audit_logs; plus tax_rates and refresh_tokens.
- **PKs are `BIGINT GENERATED BY DEFAULT AS IDENTITY`; business numbers (FLT-…, QT-…) are separate unique columns** — compact FKs, and seeds can still insert explicit ids.
- **Enums stored as `VARCHAR` + `CHECK (… IN …)`, mapped with `@Enumerated(STRING)`** — readable rows, and new values need only a migration, not a Postgres `ALTER TYPE`.
- **`created_at`/`updated_at` are `TIMESTAMPTZ`; `version BIGINT` on every mutable table, mapped with `@Version` through `BaseEntity`** — optimistic locking everywhere, not just on the three required tables.
- **`workflow_history` and `audit_logs` are append-only: `created_at` only, no version, `@Immutable`, and a trigger that rejects UPDATE/DELETE (SQLSTATE 23001)** — the audit trail can't be edited even by buggy code; 23001 surfaces as a data-integrity violation instead of "bad SQL grammar".
- **Hashes are `VARCHAR(64)` with a hex CHECK, not `CHAR(64)`** — avoids a bpchar/varchar mismatch under Hibernate `validate`.
- **One role per user (`users.role_id NOT NULL`)** — CLAUDE.md shows a single "name and role" per user and the access matrix is per role.
- **Usernames and emails are unique case-insensitively (`lower()` unique indexes); login matches case-insensitively.**
- **Quotation document `status` (DRAFT/ISSUED/SUPERSEDED/CANCELLED) is separate from `payment_status` (UNPAID/PARTIALLY_PAID/PAID)** — keeps "one ISSUED per request" literally enforceable with `ux_quotations_one_issued … WHERE status = 'ISSUED'`, and issuing is never payment.
- **Quotation CHECKs enforce `total = base + gst` and `shortfall = max(0, required − received)`; line items enforce `line_total = base + gst`** — the database catches arithmetic drift.
- **`payment_receipts.transaction_reference` is unique on `upper(trim(…))`** — "UTR123" and " utr123 " count as the same payment.
- **`tax_rates.effective_to` is exclusive and NULL means open-ended; an `EXCLUDE USING gist` (btree_gist) forbids overlapping periods per category** — at most one rate applies on any date.
- **Quotation snapshot / PDF hash / verification token columns, and SLA columns, are deferred to Phase 6 migrations** — not part of Phase 1.
- **Reference data (roles, permissions, mapping) is seeded by Flyway V6 in every environment; users only by the `dev` seeder** — the app can't work without roles, but users are environment-specific.
- **SUPERVISOR holds every permission, including the Admin Console ones** — "All modules" in CLAUDE.md, and SUPERVISOR edits SLA policies in the Admin Console.
- **Authorities = `ROLE_<code>` + permission codes; endpoints check permissions with `@PreAuthorize("hasAuthority('…')")`** — permissions express the access matrix more precisely than role names.
- **Access token: HS256 JWT via Spring's OAuth2 resource server (Nimbus), not jjwt** — first-party Spring support; one service signs and verifies, so a shared secret is enough.
- **`JWT_SECRET` (≥ 32 bytes) is required and startup fails without it; the test profile uses `${random.value}${random.value}`** — no secret is committed and there is no insecure default.
- **The server reloads the user, role and permissions from the DB on every authenticated request; the JWT `role` claim is informational only** — deactivation or a role change applies immediately rather than after 15 minutes.
- **Refresh token = 256-bit SecureRandom (base64url); only its SHA-256 is stored** — high entropy makes a slow hash unnecessary and keeps lookup by hash possible.
- **Refresh TTL is 7 days per token; each rotation issues a new 7-day token in the same family** — sliding session; the family is revoked on logout or reuse.
- **Rotation locks the token row (`PESSIMISTIC_WRITE`); a second refresh with the same token is treated as reuse and revokes the family** — strict theft detection per CLAUDE.md. The frontend must single-flight its refresh calls.
- **Rotation returns a result value instead of throwing** — so the family revocation commits before the 401 is sent.
- **The refresh cookie is `fleet_rt` with `Max-Age` 7 days; it is cleared (`Max-Age=0`) on every refresh failure and on logout.**
- **`X-Requested-With` must be present and non-blank (any value) on POST `/api/auth/refresh` and `/api/auth/logout`, enforced by a filter inside the security chain** — a custom header can't be sent cross-site without a CORS preflight, and no CORS is configured.
- **No CORS configuration** — the frontend reaches the API on the same origin through the Vite proxy.
- **Logout is `permitAll`, uses the cookie only, always returns 204 and revokes the cookie's whole family** — logout must work with an expired access token.
- **Login checks the password with BCrypt (strength 12) against a dummy hash for unknown users, and returns one generic 401 for unknown/wrong-password/inactive** — no user enumeration by message or timing. (A DaoAuthenticationProvider was planned; this is simpler and equivalent.)
- **Auth events go to `audit_logs` (LOGIN_SUCCESS, LOGIN_FAILED with the attempted username, LOGOUT, REFRESH_TOKEN_REUSE_DETECTED, USER_SEEDED)** — security-relevant actions are audited like business ones.
- **`AuditService.record` joins the caller's transaction (REQUIRED)** — business changes and their audit rows commit or roll back together; auth flows call it outside a transaction so failure audits persist.
- **Client IP is `request.getRemoteAddr()`; no `X-Forwarded-For` is trusted yet** — trusting proxy headers needs a known proxy setup.
- **Filter-level 401/403 are delegated to the MVC `HandlerExceptionResolver`** — one `GlobalExceptionHandler` renders every ProblemDetail.
- **`DataIntegrityViolationException` → 409 with a generic detail; unknown sort property → 400; optimistic-lock failure → 409** — no 500s for client-caused errors, and constraint names aren't leaked.
- **Collections return `PageResponse<T>` (content, page, size, totalElements, totalPages); max page size 100** — stable JSON instead of Spring's `Page` serialisation.
- **Dev users: `admin`, `supervisor`, `marketing.manager`, `marketing.head`, `finance` (`<username>@fleet.local`)** — a missing `DEV_*_PASSWORD` skips that user with a warning; existing users are never overwritten.
- **A `Clock` bean (UTC) is injected for token timing** — makes time-dependent logic testable.
- **Tests create users with random suffixes in `@BeforeAll`; schema tests run in rolled-back transactions** — tests share one Testcontainers DB per Spring context.

## Phase 2 — Domain services, workflow, stock allocation

- **`fleet_requests.stock_mapped_at/by` (V7)** — "qualify (stock mapped)" must be provable even when zero stock is available, so mapping is recorded explicitly rather than inferred from `allocated_qty > 0`.
- **`CHECK (production_required = quantity - allocated_qty)` (V7)** — with `allocated ≤ quantity` already enforced this is exactly `max(0, requested − allocated)`; the entity recomputes it on every quantity/allocation change and the database catches drift.
- **Request numbers `FLT-<IST year>-<n>` from `fleet_request_number_seq` starting at 1000** — one global sequence (no per-year reset) is simple and unique; starting at 1000 keeps generated numbers clear of hand-seeded ones like 0891.
- **The transition table lives in `WorkflowTransitions` (pure, unit-testable) and is applied only by `WorkflowService`** — one service owns status changes; the table covers every CLAUDE.md row, SUPERVISOR is on every human row, and QUOTATION_ISSUED → PAYMENT_PENDING is a system row applied automatically.
- **Role check before state check: a role that may never take an action gets 403 even from a wrong state; an allowed role in the wrong state gets 409** — permission is the stable property; state is transient.
- **Endpoints also carry `@PreAuthorize` permission checks; body validation (400) runs before method security, so a malformed body from an unauthorised user gets 400, a well-formed one 403** — Spring resolves arguments before the method-security proxy; nothing is executed or leaked beyond field-level validation messages.
- **Finance-row guards (issued quotation exists, approved receipts ≥ required) are deferred to the Finance phase** — the rows exist so the table and its tests are complete, but no Phase 2 endpoint can reach them.
- **CANCEL is implemented and tested at service level but has no HTTP endpoint yet** — the prompt's Phase 2 endpoint list doesn't include it; it lands with the Supervisor features.
- **RESUBMIT endpoint (`POST /{id}/resubmit`) added** — without it a rejected request could never return to marketing review.
- **Allocations are kept on reject (the request returns to marketing with its stock still held) and released on cancel** — matches CLAUDE.md ("cancel … releases stock allocations"); marketing can re-map after resubmitting.
- **Requests are editable (PATCH) only in PENDING_MARKETING_REVIEW, version required; null fields mean "no change"** — CLAUDE.md scope; clearing optional fields isn't supported yet. A variant change releases allocations and clears the stock mapping; lowering quantity below the allocation is a 409.
- **Stock mapping is a replace (`PUT /{id}/stock-allocations`), allowed only in PENDING_MARKETING_REVIEW; an empty list is valid (produce everything)** — idempotent and easy to reason about; each mapping writes a `STOCK_MAPPED` history event (from = to) and an audit row.
- **Locking order: request row first, then stock rows in ascending id; stock ids are read with a scalar query before locking** — prevents deadlocks, and avoids Hibernate returning a stale already-managed entity from a `FOR UPDATE` query.
- **Released allocations are flushed before new ones are inserted** — Hibernate executes inserts before updates, which would otherwise violate `ux_stock_allocations_active` when re-mapping the same stock row.
- **Eligible stock = same variant, active location, `available > 0`; region is ignored** — CLAUDE.md doesn't restrict allocation by region; the dealer's region can be added as a preference later.
- **Workflow transitions lock the request row (`FOR UPDATE`) and also honour an optional client `version`** — concurrent transitions serialise instead of failing late; stale UIs get a 409.
- **`PessimisticLockingFailureException` → 409** — a lock timeout or deadlock is a retryable conflict, not a 500.
- **Detail DTO includes `allowedActions` for the caller's role (guards evaluated)** — lets the UI mirror the backend; the server re-checks every action.
- **`depositReceived` = sum of APPROVED DEPOSIT receipts** — "eligible deposits" in the quotation formula; recorded-but-unapproved receipts don't count.
- **Catalogue is read-only over the API** — CLAUDE.md gives no role catalogue write access.
- **Dealer create/update require `ADMIN_DEALERS_MANAGE`; reads allow it or `FLEET_REQUEST_READ`; onboarding is one-way (never back to PENDING_ONBOARDING); `onboardedAt` is set on first activation.**
- **Business audit rows have no IP address yet** — CLAUDE.md requires actor, action, entity, before/after, reason and timestamp; IP capture can be added with a request-context helper later.
- **Audit before/after JSON is a flat snapshot of business fields with association ids only** — no lazy loading, stable shape.
- **List date filters (`createdFrom`/`createdTo`) are IST calendar days** — the business timezone.
- **Dev business seed is a Java `ApplicationRunner` (`@Profile("dev")`, `@Order(2)` after `DevUserSeeder`), idempotent by code** — the seeded request needs a real `created_by` user, which only exists after the user seeder.
- **FLT-2026-0891 is seeded unallocated** — the Swagger walkthrough then exercises stock mapping, and 30 yard units → 20 to produce is computed by the real code rather than hard-coded.
- **"Deposit available ₹10,00,000" is seeded as an APPROVED DEPOSIT receipt (`DEV-SEED-DEP-0891`) reviewed by `finance`** — the deposit lives in the payments model rather than a new column.
- **Only the Duster's category (`SUV`) gets a GST rate (18% from 2026-01-01, open-ended, flagged "must be confirmed by Finance")** — other models use other categories (COMPACT_SUV, MPV, HATCHBACK) so the seed doesn't invent rates.
- **Seed falls back to `supervisor` when `marketing.manager`/`finance` are missing, and skips the request (not master data) when no user exists** — dev startup never fails because a password env var is unset.
- **Integration tests use `TestFleetData` with random codes and real commits; the concurrency test is not `@Transactional`** — the shared Testcontainers DB stays consistent and threads really see each other's commits.

## Phase 3A — Quotations, receipts, funds verification, clearance

- **Finance guards read DB facts through a `WorkflowFacts` interface (issued quotation exists; approved DEPOSIT total)** — the transition table stays pure and unit-testable with a stub; the Spring implementation queries quotations and receipts inside the caller's transaction.
- **"approve receipts ≥ required" means approved DEPOSIT receipts ≥ the request's `requiredDeposit`** — the same "eligible deposits" figure as the quotation shortfall formula; PAYMENT-type receipts don't count toward the deposit. *Business assumption; to be confirmed with Finance* (the alternative reading is "≥ quotation total").
- **VERIFY_FUNDS happens automatically**: on receipt approval, and on issue if deposits approved earlier already cover the requirement — the approval is the Finance act; there is no separate verify endpoint.
- **GRANT_CLEARANCE re-checks that approved deposits still cover the requirement** — defence in depth; nothing un-approves a receipt today, but the guard costs one query.
- **Calculate creates a new DRAFT each time and marks earlier DRAFTs CANCELLED** — every figure Finance saw stays on record.
- **Calculation is allowed only in PENDING_FINANCE_CLEARANCE; issue only from DRAFT and only in that state** — after issue the request is PAYMENT_PENDING and the ISSUED quotation is fixed.
- **Issue re-computes the breakdown (current unit price, GST rate effective today in IST, approved deposits) and refuses a stale draft with 409** — Finance never issues figures it didn't review; recalculate, then issue.
- **One line per quotation (the request's variant × quantity); the calculator supports many lines, each rounded HALF_UP to 2 dp, then summed** — the CLAUDE.md money rule; the unit price is quantised to 2 dp before multiplying.
- **Totals must fit NUMERIC(15,2) (13 integer digits), otherwise 409** — fail early instead of a database error.
- **No GST rate for the model's category on today's IST date gives a 409 naming the category** — Finance must configure rates; nothing is defaulted.
- **Quotation validity defaults to 30 days (`fleet.quotation.validity-days`); the default terms text (`fleet.quotation.default-terms`) is a placeholder for Finance's wording.**
- **Issuing never touches money: `paymentStatus` is derived only from APPROVED receipts (UNPAID / PARTIALLY_PAID / PAID against the quotation total)** — set at issue (deposits approved earlier count) and refreshed on each approval.
- **Issued quotation amounts (deposit received, shortfall) are not changed after issue** — the document stays as issued; live figures come from receipts. The immutable snapshot and PDF hash arrive in Phase 6.
- **Numbers: `QT-<IST year>-<5+ digits>` and `RCPT-<IST year>-<5+ digits>` from sequences (V8).**
- **Receipts can be recorded and approved only in PENDING_FINANCE_CLEARANCE, PAYMENT_PENDING and FUNDS_VERIFIED** — the finance stages; later balance payments can be added with dispatch.
- **Duplicate references are rejected twice over: a pre-check with the same `upper(trim())` normalisation as the unique index (clear 409), and the index itself (a concurrent loser gets the same 409)** — duplicate-payment protection can't be bypassed, including by SUPERVISOR.
- **`receivedDate` can't be after today in IST, checked in the service rather than with `@PastOrPresent`** — the JVM runs in UTC, which would reject valid IST dates for 5½ hours each night.
- **Approval locks the request row, then the receipt row (`FOR UPDATE`), reading the request id by scalar query first; a non-RECORDED receipt is 409** — same lock order as every other write; concurrent approvals serialise and exactly one wins.
- **No reject-receipt endpoint and no maker-checker rule (the recorder may approve) yet** — not in the Phase 3A brief; worth adding if Finance needs segregation of duties.
- **Readers: quotations need `QUOTATION_READ` (FIN, MH, SUP); receipts need `PAYMENT_RECORD` or `DEPOSIT_REVIEW`, so the Marketing Head can review deposits.**
- **Every quotation calculation, issue, receipt record and approval writes an audit row with before/after JSON and a `workflow_history` event (QUOTATION_CALCULATED, RECEIPT_RECORDED, RECEIPT_APPROVED; transitions as usual).**
- **Finance tests give each world its own vehicle category and GST rate** — tax-rate periods can't overlap per category, and the shared test DB must not collide with `MigrationSchemaTest`'s rolled-back T_SUV rate.

## Phase 3B — Production, dispatch, completion, Admin Console APIs, Supervisor powers

- **Production orders are always for exactly `productionRequired` units at the request's plant (or a given active plant); scheduling runs the workflow transition first** — the NEEDS_PRODUCTION guard gives the clear 409 "No production is required; schedule dispatch instead" before anything is created.
- **Dispatch is for the full request quantity; scheduled dates can't be in the past (IST)** — one shipment per request for now; split deliveries can come later.
- **COMPLETE closes everything in the same transaction: production orders COMPLETED, dispatches DELIVERED (dispatched/delivered at completion time), ACTIVE allocations CONSUMED and the stock rows' allocated count reduced (locked in id order)** — the yard units physically leave; available was already reduced at allocation.
- **Cross-feature side effects of transitions live in `TransitionEffects` (REJECT reason; CANCEL; COMPLETE)** — keeps `WorkflowService` small; same transaction and request lock.
- **CANCEL also voids open work: DRAFT/ISSUED quotations → CANCELLED, SCHEDULED/IN_PROGRESS production orders and SCHEDULED dispatches → CANCELLED; approved receipts stay recorded** — refunds are out of scope; money records are never deleted.
- **Override = `POST /{id}/override` with `{reason, version?, changes:{field:value}}`; the allow-list is requiredDeposit, productionEstimateWeeks, requestedDeliveryDate, plantId, notes. Any other key (status, quantity, allocation, production, variant, …) is a 400 naming the field** — overrides can't bypass the workflow, stock locking, tax calculation or duplicate-payment protection.
- **Override values arrive as strings (`Map<String,String>`), and money is parsed from the literal text with BigDecimal** — a JSON number never passes through `double`.
- **Overrides work in any non-terminal state (409 when COMPLETED/CANCELLED), write an `OVERRIDE` audit row (before/after JSON, reason) and an `is_override = true` history row (from = to)** — CLAUDE.md audit rule; the database CHECK already requires a reason for override rows.
- **After an override, funds verification is re-evaluated** — a lowered deposit requirement may already be covered in PAYMENT_PENDING.
- **Reassign needs a reason and an active non-ADMIN assignee; it is audited (REASSIGN) and recorded in history (REASSIGNED)** — reassigning to someone without fleet access would orphan the request.
- **Cancel is `POST /{id}/cancel` (`REQUEST_CANCEL`) through the WorkflowService** — one path for state changes.
- **Only a SUPERVISOR can create, edit, (de)activate or grant the SUPERVISOR role; ADMIN gets 403** — otherwise an ADMIN could create a Supervisor account and gain operational access, which CLAUDE.md denies ADMIN. *Security choice; please confirm.*
- **Nobody can change their own role or (de)activate themselves (409)** — prevents accidental lock-out and self-escalation.
- **Deactivation revokes every live refresh token (reason USER_DEACTIVATED); access tokens already stop at the next request because authorities are reloaded from the database** — immediate lock-out.
- **New-user passwords are 12–128 characters and must not contain the username; they are BCrypt-hashed and never returned, logged or audited** — UserDto has no hash field; audit JSON is built from UserDto.
- **Activation endpoints are idempotent: setting the current value returns 200 and writes no audit row.**
- **Audit search filters: actorId, actorUsername (case-insensitive), action, entityType (case-insensitive), entityId, from/to (IST days, inclusive); newest first; paginated** — read-only over the append-only table.
- **ADMIN's lack of operational access comes from the permission model (V6) and is proven by a test that sweeps every operational endpoint with a well-formed body** — the 403 must come from authorisation, not body validation.

## Phase 4 — Frontend auth, shell, UI kit

- **Access token in a module variable in `lib/api.ts`, never in storage; on reload the session is restored by calling `/auth/refresh` (cookie) before `/auth/me`** — CLAUDE.md memory-only rule.
- **Single-flight refresh: concurrent 401s share one refresh promise; across tabs, `navigator.locks` serialises refreshes when available** — a rotated refresh token sent twice would trigger reuse detection and revoke the family.
- **`X-Requested-With: XMLHttpRequest` is a default header on every API call, not only refresh/logout** — simpler, harmless on other endpoints.
- **A 401 retries once after refresh; auth endpoints are flagged `skipAuth` and never trigger a refresh; 403 never refreshes** — no loops.
- **The current user is one TanStack Query (`['auth','me']`, staleTime ∞) and is passed down by `RequireAuth` through context** — children only render while a user exists, so logout can't crash the shell mid-redirect (found by a test).
- **Ending a session sets `me` to null first, then removes all other cached queries** — no cross-user data survives logout or session expiry.
- **Navigation, route guards and the post-login landing page share one `NAV_ITEMS` list keyed on permission codes from `/me` (not role names)** — mirrors the backend's permission checks; the server stays the authority.
- **Unpermitted URLs redirect to `/forbidden` (403 page) with the attempted path; unknown URLs show a not-found page inside the shell.**
- **Module pages are placeholders in Phase 4; their screens come in later phases.**
- **Dev role simulator not built** — optional per CLAUDE.md and grants nothing; skipped to keep scope.
- **Desktop sidebar collapse uses motion `layout` (FLIP transforms) rather than animating width** — honours the transform/opacity-only rule.
- **Page transitions use `AnimatePresence mode="popLayout"`, so the new page appears immediately while the old one fades** — no animation delays input.
- **Theme: `system | light | dark` stored in localStorage (UI preference only), applied by an inline script before first paint; semantic colour tokens (`bg-surface`, `text-fg`, …) swap under `.dark`.**
- **Queries don't retry on 4xx; once on network/5xx.**
- **Toasts, dialogs, drawer and focus trap are hand-written (no extra UI library); `motion` 14.1.0 is the only new dependency.**
- **Tests stub HTTP with a custom Axios adapter (`test/fakeServer.ts`), so the real interceptors run** — the refresh logic is exercised, not mocked.

## Phase 5A — Dashboard cards, fleet table, request drawer

- **New `GET /api/fleet-requests/summary` (FLEET_REQUEST_READ), one `GROUP BY status` query; stage buckets are fixed server-side (marketing: review/returned/qualified; executive: pending/approved; finance: clearance/quotation/payment/funds; operations: cleared/production/dispatch)** — the dashboard figures are the backend's, not the browser's.
- **The six cards are Active, Marketing review, Executive approval, Finance, Production & dispatch, Units to produce (sum of `productionRequired` on non-terminal requests)** — order value needs issued quotations and belongs to the Phase 6 executive dashboard.
- **Summary is global (not filtered by the table filters)** — cards act as stage shortcuts; clicking one filters the table.
- **New read endpoints `GET /api/fleet-requests/{id}/production-orders` and `/dispatches` (FLEET_REQUEST_READ, paginated) and `GET /api/regions` (FLEET_REQUEST_READ or ADMIN_DEALERS_MANAGE), `GET /api/plants` (FLEET_REQUEST_READ)** — the Schedule tab and table filters had no data source; read services are separate from the write services.
- **Fleet modules (Fleet Evaluation, Executive Approval, Finance, Production & Dispatch) share one workspace, each opening on its own stage filter; the user can widen it** — one table implementation, role-appropriate default.
- **All filters, sort, page and the open request (`?request=<id>`) live in the URL** — views are shareable and survive reload.
- **Sortable columns use entity property paths the backend already accepts (`requestNumber`, `dealer.name`, `quantity`, `productionRequired`, `requestedDeliveryDate`, `status`, `createdAt`, `updatedAt`); on mobile a Sort select replaces the headers** — unknown sorts are a 400, verified by test.
- **Drawer tabs are hidden when the user lacks the read permission (Finance: QUOTATION_READ; Payments: PAYMENT_RECORD or DEPOSIT_REVIEW; Audit: AUDIT_LOG_READ, using the existing admin audit search filtered to the request)** — showing them would only produce 403s; no new audit exposure was added.
- **Editability mirrors the backend: details and stock in PENDING_MARKETING_REVIEW with FLEET_REQUEST_WRITE / STOCK_MAP; quotation calculate/issue in PENDING_FINANCE_CLEARANCE with QUOTATION_ISSUE; receipts in the finance stages with PAYMENT_RECORD / PAYMENT_APPROVE; production/dispatch scheduling only when the server lists the action in `allowedActions`** — scheduling guards (e.g. nothing to produce) are evaluated by the server.
- **Workflow transitions (qualify, approve, reject, forward, clearance, cancel) are shown as "next steps" only; their buttons are not in 5A.**
- **Money is sent as decimal strings and only formatted (never calculated) in the browser; dates are shown in IST, `LocalDate` values without time-zone shifting.**
- **Stock mapping keeps rows this request fully allocated (0 available, so absent from `stock-options`) editable** — otherwise saving would silently release them.
- **`DataTable` gained optional sortable headers (`sortKey`, `aria-sort`) instead of a new component; feature-local tabs and metric cards live under `features/fleet`** — Phase 5A rule: no new base components.

## Phase 5B — Workflow actions, finance and scheduling flows

- **Workflow buttons live in the drawer footer and come only from the server's `allowedActions` (role + state + guards); a fixed map turns each code into a label, endpoint and confirmation text** — the backend stays the authority; the UI never invents a transition.
- **Every transition (qualify, forward, resubmit, approve, reject, forward to Finance, grant clearance, complete) goes through a ConfirmDialog; Reject requires a reason in the dialog (the server also requires it)** — none of them can be undone from the UI.
- **Recording a receipt and scheduling production/dispatch also confirm first (receipts can't be deleted and references are single-use; scheduling moves the workflow). Stock mapping, edits and quotation calculation don't confirm** — they can be redone.
- **`ISSUE_QUOTATION` is never offered in `allowedActions` before issue (its guard needs an issued quotation — seen in a live run), so the footer's "Quotation…" and "Receipts…" shortcuts follow the same role + state rules as the tabs** — otherwise Finance would see no footer action in PENDING_FINANCE_CLEARANCE.
- **System steps (AWAIT_PAYMENT, VERIFY_FUNDS) never get buttons; CANCEL and other Supervisor overrides are left to the override phase.**
- **Every mutation invalidates the whole `['fleet']` cache (row, summary, detail, tabs) and shows a success toast or the ProblemDetail as an error toast; a 409 says the data was reloaded.**
- **The quotation view shows the backend's lines (qty, unit price, base, GST, line total), totals, deposit shortfall and terms exactly as returned; the browser formats but never computes money.**
- **Only the top-most overlay handles Escape/Tab (a stack in `useOverlay`)** — a confirmation over the drawer closed both before.
- **The toast container is a named `region` ("Notifications")** — screen readers can find it, and tests can tell a toast from a status badge with the same words.

## Phase 5C — Admin Console and Supervisor override

- **New read-only `GET /api/admin/roles` (ADMIN_USERS_MANAGE): roles with their permission codes** — roles and grants come from migration V6; the console shows them but cannot edit them (editing permissions was not in scope and would be a security change).
- **Admin Console tabs follow permissions: Users and Roles need ADMIN_USERS_MANAGE, Dealers ADMIN_DEALERS_MANAGE, Audit log AUDIT_LOG_READ; the selected tab is in the URL (`?tab=`).**
- **User rules mirror the server: only a Supervisor sees the SUPERVISOR role option or can edit a Supervisor account; nobody can change their own role or (de)activate themselves. (De)activation is confirmed. Passwords are only entered on create (12–128 chars, not containing the username) and are never shown again.**
- **Dealer onboarding mirrors the server patterns (code, GSTIN, phone, PIN); a status change (pending / active / suspended) is confirmed because only ACTIVE dealers can be used on new requests (checked in `FleetRequestService.create`).**
- **The audit log viewer is read-only with debounced text filters (actor, action, entity type, entity id) and a date range; a row opens before/after JSON, actor role, IP and reason.**
- **Override is a Supervisor-only switch in the request drawer (WORKFLOW_OVERRIDE, non-terminal states); turning it on shows a red banner and replaces the tabs with the override form for the five allow-listed fields only** — nothing else is offered, and the server refuses other fields anyway.
- **An override needs a reason and at least one changed field; a confirmation lists each changed field's current and new value with the reason; only changed fields are sent, and cleared optional fields are sent as `null`.**
- **The override audit trail is read from the request's audit rows (action OVERRIDE), diffing before/after JSON** — no new endpoint; Supervisors already hold AUDIT_LOG_READ.
- **Supervisor Cancel is now a footer action (from `allowedActions`) with a required reason.** Reassign UI is not built yet.
- **Shared pieces promoted: `components/ui/Tabs` (used by the drawer and Admin Console) and `lib/reportError`; `Dialog` descriptions render in a `<div>` so they can hold a table.**

## Phase 6A — SLA timers

- **SLA hours are calendar hours in IST (`Asia/Kolkata`); since India has no DST, "entered + N hours" on an instant equals N IST hours. Business-hours counting is out of scope** — CLAUDE.md.
- **`sla_policies` (V10) has one row per timed stage with the CLAUDE.md defaults, seeded in every environment (business configuration, like roles). Stages without a row — RETURNED_TO_MARKETING, EXECUTIVE_APPROVED, QUOTATION_ISSUED, PRODUCTION_SCHEDULED, DISPATCH_SCHEDULED — and terminal states have no SLA (`slaStatus` null)** — only the listed stages were given limits.
- **The clock is frozen on stage entry: `stage_entered_at`, `sla_warning_at` and `sla_due_at` are stored on the request. Policy edits apply to stages entered afterwards; running clocks keep their deadlines** — predictable for users, and what "store sla_due_at on entry" implies.
- **AT_RISK starts at `hours × threshold%`, rounded down to the minute; BREACHED at or after the due instant (both boundaries inclusive).** An inactive policy starts no clock.
- **Every status change goes through `WorkflowService.apply` (and `create`), which calls `SlaService.enterStage` in the same transaction** — one place, so no transition can skip the clock.
- **Existing open requests are backfilled in V10 from the last history row that moved them into their current status (same-status events like RECEIPT_RECORDED ignored), else `updated_at`.** Already-overdue backfilled clocks get their breach event on the first scan.
- **Breach scan every 5 minutes (`fleet.sla.breach-scan.*`, off in the test profile; tests call `SlaBreachJob.scan()`). Each breach is claimed with a conditional `UPDATE … WHERE sla_breached_at IS NULL AND stage_entered_at = :entry`, and the `SLA_BREACHED` history row is written in the same transaction; a partial unique index on `(fleet_request_id, metadata->>'stageEnteredAt') WHERE action = 'SLA_BREACHED'` is the database backstop** — "never record the same breach twice", even with concurrent instances. Re-entering a stage resets the claim.
- **The breach claim is a bulk update that doesn't bump `@Version`** — a background job must not make a user's next edit fail with 409.
- **`SLA_BREACHED` is a system event: history row with no actor and from = to = current status, metadata `{stageEnteredAt, dueAt, detectedAt}`; no audit_logs row** — nothing a user did changed; the brief asks for the workflow_history event.
- **`slaStatus` (plus `stageEnteredAt`, `slaDueAt`, and `slaWarningAt` on detail) is in the list and detail DTOs; `sla=` filters the list (repeatable: ON_TRACK, AT_RISK, BREACHED = "Overdue") with the same boundaries in SQL; requests without an SLA never match.**
- **The summary adds `slaAtRisk`, `slaBreached` and `slaByStage` (marketing / executive / finance / operations), computed in SQL; each module's header shows its own stage's "N at risk · M overdue", which filters the table.**
- **SLA policies: `GET/PATCH /api/admin/sla-policies` with SLA_POLICY_MANAGE (Supervisor only), validated (1–8760 h, 1–99 %, also as DB CHECKs), optimistic-locked and audited (`SLA_POLICY_UPDATE`, entity `SLA_POLICY`, before/after).**
- **UI: the chip's colour and status come only from the server; the text ("18h left", "Overdue 6h", "2d 4h left") is counted down by a single shared one-minute client timer, and fleet list/summary/detail refetch every minute. If the client clock runs out before the server flags a breach, the chip reads "Due now". Overdue chips pulse with opacity only, off under reduced motion.**
